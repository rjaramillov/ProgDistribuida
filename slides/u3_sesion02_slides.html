Así se ve un code review · sus fichas contra una guía real

No son manías del profe: son reglas publicadas

Zalando (comercio electrónico, Europa) publica las reglas que deben cumplir todas sus APIs. Sus fichas, revisadas con esa guía:

errores: 404, 422, 500

[220] MUST use most specific HTTP status codes. Un 500 no se planea: es un bug.

POST /api/classes/join

[141] MUST keep URLs verb-free y [135] SHOULD not use /api as base path. Mejor POST /clases/{codigo}/alumnos.

PUT /reactions/… aplica o quita

[229] SHOULD consider to design POST and PATCH idempotent. Un interruptor no lo es: que diga el estado, {"activa": true}.

Recursos: usuarios individuales…

[138] MUST avoid actions — think about resources y [134] MUST pluralize resource names. El recurso es lo que se maneja: tareas.

GET /api/login

Con GET la contraseña viaja en la URL: queda en el historial y en los registros del servidor. El login va con POST.

errores: -

Todo endpoint puede fallar: como mínimo 404 y 422. Lo corrigen en el bloque 00.

Zalando SE (s.f.): número de regla entre corchetes · Corrección mía: POST /auth/login → 200 está bien
“La idempotencia aún no me queda claro qué relevancia tiene” · un compañero, el jueves

Aquí está la relevancia: las peticiones se reintentan solas

Amazon Web Services

Al pedir un servidor nuevo, la respuesta puede perderse por un timeout. Las herramientas de AWS generan un identificador (ClientToken) y lo reusan al reintentar: el segundo intento regresa el mismo servidor en lugar de crear otro, y cobrarlo.

Stripe (pagos)

Cada cobro lleva el encabezado Idempotency-Key. Si la app reintenta con la misma llave, Stripe regresa el resultado del primero y no cobra dos veces. Zalando lo pide en su regla [230].

En sus proyectos: no es “cualquier GET” (un GET nunca hace daño). Es el endpoint que escribe y duele si se repite: POST /pedidos/{id}/pagos, POST /ventas, POST /boletos. Lo vuelven a pensar en el bloque 00.
Featonby (s.f.), AWS Builders’ Library · Stripe (s.f.) · Zalando SE (s.f.), regla 230

El dato malo entró por una puerta y tronó en otra. El reporte no tiene ningún bug: el problema fue el POST que dejó entrar "abc" donde iba un número. Y ese 500 le va a salir a todos los usuarios hasta que alguien limpie la base de datos a mano.

Pregunta 1 · Por qué validar no es solo “que no truene”

Validar en la entrada también es seguridad

Validar es revisar los datos de una petición al entrar, antes de hacer nada con ellos, y rechazar con un error claro lo que no cumple las reglas. Lo que no está en las reglas, no se guarda.

Sin validar: guarda lo que le manden

POST /sin-validar/equipos {"nombre": "Arduino Mega", "estado": "prestado", "precio": -50} → 201 {"nombre":"Arduino Mega", "estado":"prestado","precio":-50}

Validando: solo lo que dicen las reglas

POST /equipos {"nombre": "Arduino Mega", "tipo": "arduino", "inventario": "LAB-030", "estado": "prestado", "precio": -50} → 201 {…,"inventario":"LAB-030", "estado":"disponible"}
Que el cliente pueda cambiar campos que no le tocan (estado, rol, precio) está en el OWASP API Security Top 10, la lista de los riesgos más comunes en APIs: es el API3:2023 (antes llamado mass assignment).

Pregunta 2 · ¿Qué se valida?

Cuatro filtros, cada uno con su código

FILTRO 1

¿Se entiende el mensaje?

400

El JSON está roto: {"nombre": ,,}

FILTRO 2

¿Están los datos y tienen la forma correcta?

422

Falta el nombre, el precio es "abc" o es negativo.

FILTRO 3

¿Existe lo que pide la ruta?

404

GET /equipos/99 y no hay equipo 99.

FILTRO 4

¿Choca con lo que ya hay?

409

Prestar un equipo que ya está prestado.

Una regla útil: si lo que no existe viene en la ruta (/equipos/99) es 404. Si viene en el cuerpo ({"equipo_id": 99}) es un dato inválido: 422.
Fielding et al. (2022), RFC 9110 §15.5.1, §15.5.5, §15.5.10 y §15.5.21

Pregunta 3 · ¿Qué respondo cuando algo falla?

Un formato de error del equipo, y nunca la traza

Lo correcto: siempre la misma forma

HTTP/1.1 422 Unprocessable Entity {"error": "Los datos no son válidos", "detalles": ["nombre: mínimo 2 caracteres", "inventario: formato LAB-000"]}

El front escribe un solo código para mostrar errores. Zalando exige un formato estándar, Problem JSON ([176], RFC 9457). En el curso usamos uno más simple; lo importante es que sea siempre el mismo.

Lo que no: Express sin manejador de errores

HTTP/1.1 400 Bad Request Content-Type: text/html <pre>SyntaxError: Unexpected token ',' at JSON.parse (<anonymous>) at parse (/home/…/node_modules/body-parser/…

No es JSON y muestra rutas internas del servidor. Zalando: [177] MUST not expose stack traces. OWASP lo marca como riesgo (API8:2023). Y un 500 por un dato malo no es validación: es un bug.

Para no llegar novatos · preguntas típicas de una entrevista de backend

Después de hoy, ya las pueden contestar

“¿Por qué validar en el backend si el front ya valida?”Porque al backend le pueden llegar peticiones sin pasar por el front. El front valida por comodidad; el backend, por protección.
“¿Qué diferencia hay entre 400, 422 y 409?”400: no se entiende el mensaje. 422: se entiende, pero los datos no cumplen las reglas. 409: los datos están bien, pero chocan con lo que ya hay.
“¿Qué es la idempotencia y dónde la cuidarías?”Repetir la petición deja los datos igual. La cuido en los pagos y en todo lo que el cliente pueda reintentar.
“¿Qué pasa si a tu API le llega un dato malo?”Responde 4xx con un formato de error claro; nunca un 500 ni la traza del error.
“¿Cómo sabes que tu API funciona antes de entregarla?”Con pruebas automáticas que corren en cada cambio, no probando a mano en Postman.

Cierre · el gancho

¿Validar también en la API? La B.

El jueves ustedes le mandaron peticiones a una API sin ningún formulario: con /docs y con un socket. Cualquiera puede hacer lo mismo con su API: con Postman, con curl, con un script.

El front valida para ayudar al usuario. La API valida para proteger los datos. Si solo valida el front, la API no tiene defensa.

Llévense esto

  • Nunca confíes en lo que llega: valida al entrar.
  • Cuatro filtros: 400 · 422 · 404 · 409. Un 500 es un bug.
  • El código entra con pruebas y con revisión, no “porque funciona”.

Jueves 5: base de datos y Swagger. En una empresa, otros equipos van a usar su API leyendo su documentación.
