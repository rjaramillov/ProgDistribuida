¿Qué pasa si dos clientes intentan conectarse a la vez al servidor de la sesión 6?

Uno de los dos se va a quedar esperando — y hoy van a ver por qué.

El problema

Un servidor, un cliente a la vez

Servidor de un solo hilo

SERVER
A
Atendiendo ahora
B
Esperando su turno…

Con threading (hoy)

SERVER
A
Atendiendo en su hilo
B
Atendiendo en OTRO hilo

El servidor de la sesión 6 llama a accept(), luego atiende a ese cliente por completo, y hasta entonces regresa a accept() — B no tiene alternativa más que esperar.

La solución

Un hilo por cliente

💡 Toca cualquier bloque para ver su explicación completa
Nuevo: sumamos threading 
import socket, threading
① Qué hacer con cada cliente 
def atender_cliente(conexion, direccion):
    datos = conexion.recv(1024)
    conexion.send("Recibido".encode())
    conexion.close()
Repaso — preparar el servidor 
servidor = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
servidor.bind(("localhost", 5000))
servidor.listen()
Nuevo: nunca dejar de escuchar 
while True:
    conexion, direccion = servidor.accept()
② ③ Lanzar un hilo por cliente 
    hilo = threading.Thread(
        target=atender_cliente,
        args=(conexion, direccion)
    )
    hilo.start()
Trampa de sintaxis: target=atender_cliente va SIN paréntesis. Le están pasando la función misma, no el resultado de llamarla — Thread se encarga de llamarla después, en su propio momento. Si alguien escribe atender_cliente() aquí, Python la ejecuta de inmediato y Thread recibe lo que esa función devuelve (nada), no la función.
1

Lo que antes corría directo en el while, ahora vive en una función aparte — es lo que va a correr en paralelo.

2

threading.Thread crea un hilo nuevo, listo para ejecutar esa función con ese cliente específico.

3

start() arranca el hilo — y el ciclo principal regresa de inmediato a accept() por el siguiente cliente.

🤔 Antes de seguir: ¿qué pasaría si alguien olvida escribir hilo.start()?
El objeto Thread se crea, pero nunca corre — es como escribir una función y nunca llamarla. Ese cliente se queda esperando una respuesta que jamás llega, y no hay ningún error que avise por qué.
Lo que threading no resuelve solo

Manejo de errores por hilo

Sin try/except — esto imprime la terminal, y nadie se entera 
Exception in thread Thread-3 (atender_cliente):
Traceback (most recent call last):
  File "servidor_multi.py", line 4, in atender_cliente
    datos = conexion.recv(1024)
            ^^^^^^^^^^^^^^^^^^^
ConnectionResetError: [Errno 104] Connection reset by peer

El hilo de ese cliente muere solo — el servidor y los demás clientes siguen sin problema. Eso ya lo hace threading por su cuenta. El silencio es el problema real: nadie se entera, y ese socket nunca se cierra.

💡 Toca cualquier bloque para ver su explicación completa
def atender_cliente(conexion, direccion):
① Vigilar mientras el cliente hable 
    try:
        while True:
            datos = conexion.recv(1024)
            if not datos:
                break
            # ...procesar datos...
② Si se cae abruptamente 
    except ConnectionResetError:
        print(f"{direccion} se desconectó mal")
③ Cerrar pase lo que pase 
    finally:
        conexion.close()
📘 Guía de consulta: try/except aparece por primera vez hoy — la sección correspondiente de la guía Python para sockets tiene otro ejemplo si lo necesitas repasar en casa.
1

Que un hilo truene sin tumbar a los demás ya lo regala threading. Este try resuelve algo distinto: que el error no se pierda en silencio.

2

Bytes vacíos (b'') significa que el cliente cerró la conexión limpiamente — con close().

3

Si el cliente se desconecta abruptamente (se cae la red, cierran la terminal), Python lanza ConnectionResetError — lo nombramos para responder con un mensaje claro, no para "salvar" a los demás hilos.

4

finally se ejecuta siempre. Sin él, el socket de un cliente que falló se queda abierto para siempre — una fuga de recursos silenciosa.

🤔 Si esto pasa muchas veces sin finally, ¿qué le pasa al servidor con el tiempo?
Cada socket sin cerrar sigue ocupando un descriptor de archivo del sistema operativo. Con suficientes clientes fallando así, el servidor puede quedarse sin descriptores disponibles — y empezar a rechazar conexiones nuevas, aunque el código "funcione".
