RPC
Remote Procedure Call · en español: llamada a procedimiento remoto (procedimiento = función)
Técnica para que un programa llame a una función que se ejecuta en otra computadora, escribiéndola igual que si fuera una función local.

🍽️ En el restaurante

Pedir un platillo sin entrar a la cocina.

Lo que NO es

No es un lenguaje ni un programa: es una idea. gRPC es una herramienta que la implementa.

Dónde lo verán

Stub
se pronuncia “stab” · en español: representante local
Pieza de código en tu computadora que tiene los mismos nombres de función que el servicio remoto. Tu programa la llama como a cualquier función; ella empaqueta los datos, los manda al servidor y te devuelve la respuesta.

🤵 En el restaurante

El mesero: le hablas como si fuera el cocinero, pero solo lleva tu pedido.

Lo que NO es

No es el servidor ni la función real. No hace la suma: solo la pide.

Marshalling
se pronuncia “márshaling” · en español: empaquetar o serializar
Convertir la llamada (qué función y con qué datos) en bytes con un formato acordado, para que pueda viajar por la red. El paso de regreso, del otro lado, se llama unmarshalling (desempaquetar o deserializar).

Contrato
también: interfaz · en inglés: interface o service definition
Definición en código de qué funciones existen, qué datos reciben y qué devuelven. Cliente y servidor comparten el mismo contrato: si no coincide, no se entienden.

Preparando la llamada…

El cliente llama al stub; el stub empaqueta (marshalling) y envía por la red; del otro lado se desempaqueta, se ejecuta la función real y el resultado regresa por el mismo camino.

Para tu código no hay diferencia visible entre una llamada local y una remota: solo escribes sumar(2, 3).

📥 ¿Y el skeleton?

En el RMI original, del lado del servidor, había otra pieza: el (quien lee la comanda en cocina). Hoy RMI ya no genera esa clase aparte, pero su papel sigue ahí.

Fíjense en ①: es un contrato, pero escrito en Java y solo para Java. El jueves van a escribir ese mismo contrato en un archivo .proto que entiende cualquier lenguaje.
De dónde viene esto

40 años resolviendo el mismo problema

1984
RPC
Birrell y Nelson (Xerox PARC) formalizan la idea y el stub.
1991
CORBA
Intento de estándar entre lenguajes; tan complejo que se usó poco.
1997
Java RMI
RPC para Java… pero solo entre programas Java.
2002
.NET Remoting
RPC para .NET… pero solo entre programas .NET.
2015
gRPC
De Google, abierto: cualquier lenguaje, con un contrato .proto.
No se memorizan fechas. Importa el patrón: todas buscaban lo mismo — llamar funciones remotas fácilmente — y ganó la que funciona entre cualquier lenguaje.
Por qué quedaron atrás

El problema fue la

Java RMI

Java ⇄ Java✓ funciona
Java ⇄ Python✗ no

.NET Remoting

.NET ⇄ .NET✓ funciona
.NET ⇄ Java✗ no

gRPC

Python ⇄ Java ⇄ Go ⇄ C#✓ todos
cada lenguaje genera su código desde el mismo .proto
  • Atadas a una sola : cliente y servidor tenían que estar escritos en lo mismo.
  • Riesgos de seguridad: la automática de objetos resultó ser una fuente conocida de vulnerabilidades.
  • .NET Remoting ya no existe en las versiones modernas de .NET (desde .NET Core).
  • ¿Y REST? Es la otra gran solución: en vez de llamar funciones, pides recursos por HTTP (GET, POST). La verán a fondo en la Unidad III.
